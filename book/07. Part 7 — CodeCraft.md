# Part 7. CodeCraft — 요구사항에서 설계까지

> Part 1~6이 "AI를 어떻게 안전하고 정확하게 일하게 만들 것인가"였다면,
> Part 7은 **"그래서 무엇을 만들게 할 것인가"를 사람이 먼저 판단하는 법**이다.
> **모델보다 Harness가 중요하고, 코드보다 요구사항(Requirements) Harness가 먼저다.**

# 15장. Code Craft와 5단계 루틴

> **Code Craft는 알고리즘 테스트가 아니라, 제품과 시스템 관점에서 문제를 풀어가는 실무형 문제 해결 전략이다.**

정답 코드를 빠르게 짜는 능력이 아니라 **요구사항 해석 → 구조 설계 → 트레이드오프 판단 → 확장 가능한 구현** 능력을 기른다. DoorDash·Uber·Stripe·Netflix·Amazon 같은 기업이 실제 서비스에서 마주치는 문제를 이렇게 다룬다.

| | 알고리즘 문제 풀이 | Code Craft |
|---|---|---|
| 목적 | 제한 시간 안에 정답 코드 | 문제 해석 + 설계·구현·검증 |
| 초점 | 투 포인터, BFS/DFS, DP, HashMap | 요구사항, 구조, 트레이드오프, 확장성 |
| 결과물 | 정답 코드 하나 | 코딩 실력 + 설계 사고 + 설명 능력 |

**Code Craft가 확인하는 것**: 요구사항을 제대로 이해했는가 · 애매한 부분을 명확히 할 수 있는가 · 바로 코딩하지 않고 구조를 먼저 설계하는가 · 기능 추가·수정에 유연한 구조와 유지보수성을 고려하는가 · 예외 상황을 생각하는가 · 작성 후 검증할 수 있는가 · 자신의 설계를 논리적으로 설명할 수 있는가

## 15.1 하나의 카테고리로 끝나지 않는다

OOD · API 디자인 · Low-Level Design · Product Design · System Design이 **서로 연결된 사고 과정**이다.

**예 1 — DoorDash Payout 계산.** 바로 구현하지 말고 먼저 묻는다.

* Payout은 어떤 요소로 구성되는가 (거리, 시간, 보너스, Peak Time, 팁)
* 환불·취소된 주문은 어떻게 처리하는가
* 정산 금액의 소수점은 어떻게 처리하는가
* 정책이 자주 바뀔 수 있는가

> 실제 회사에서는 요구사항이 완벽하게 주어지지 않는다. **애매한 부분을 구조화하고, 변경 가능성이 높은/낮은 부분을 나눠 우선순위를 판단**할 수 있어야 한다.

**예 2 — Spotify 플레이리스트 매니저.** 겉보기엔 단순 CRUD지만 조금만 깊이 들어가면 API 디자인 문제가 된다.

* 플레이리스트는 어떻게 생성되는가 / 곡은 어떤 입력·방식으로 추가되는가
* 순서를 바꾸는 API는 어떤 방식이 좋은가 / 같은 곡을 중복으로 넣을 수 있는가
* 수백만 명이 동시에 쓸 때 순서 정보 저장·캐시·동시 추가 충돌은?

> **올바른 질문을 던져야 올바른 답을 얻는다. 스스로 질문하고 판단하는 능력이 먼저다.**

## 15.2 5단계 루틴

> **어떤 문제가 나와도 Explore → Brainstorm → Plan → Implement → Verify만 따라가면 풀 수 있다.**

문제를 듣자마자 코딩하지 않는다. 방향을 잡고 → 옵션을 비교하고 → 구조를 짜고 → 구현하고 → 검증한다. Claude Code의 `Explore → Plan → Edit → Verify`(3장)와 같은 형태의 루프다.

**① Explore — 방향부터 확실히**

* 제품 요구사항 (기능적 요구사항)
* **Clarifying Question** — 조심할 설계 사항·애매한 엣지 케이스를 명확한 질문으로 되묻고, 비즈니스 정책·UI/UX 판단의 명확성을 확보
* **입력/출력 정의** — 입력은 어디서 오는가, 어떤 데이터가 들어가 어떤 결과가 나오는가, 출력 형식은
* **제약조건** — 최댓값/최솟값 등 데이터 제한
* **예외 상황** — 예상치 못한 입력/상태
* **변경 가능성이 높은 부분 찾기**
* **최소 구현 범위(MVP) 정하기**
* **확장 가능성 고려**

> 목표는 "코딩"이 아니라 **"방향"**을 확실히 잡는 것.

**② Brainstorm — 설계 옵션 비교**
하나의 답이 아니라 여러 옵션의 트레이드오프를 비교한다. 예: Option A는 "빠르고 읽기 쉽다"지만 "규칙이 늘면 복잡해진다", Option B도 똑같이 장단점을 정리해 비교 → **현재 요구사항에 맞는 합리적 옵션을 선택.**

**③ Plan — 선택한 설계를 구조화**
예: 핵심 도메인 객체 A·B·C를 나눈다면 A는 데이터 표현, B는 계산, C는 정책 캡슐화. 변경 가능성이 높은 부분을 어떻게 처리할지도 여기서 계획한다.

> **책임(Responsibility) 배분이 핵심.** 결제 모듈이 결제 말고 다른 것까지 책임지면 좋은 설계가 아니다.

**④ Implement — 코드 구현**
어떤 언어로 · Class/Method/Enum/Data Type 설계 · 예외 처리 · **읽기 쉽고 테스트 가능하고 확장 가능한 구조로**

**⑤ Verify — 요구사항을 만족하는지 증명**
"코드가 돌아간다"가 아니라 **요구사항을 만족하는지 증명**하는 단계.
Happy Path · Edge Case · Invalid Input 대응 · 성능 · 확장성

> Edge Case 대응: 유효하지 않은 입력·빈 데이터·중복·기능 실패를 **어떻게 처리할지 결정**한다. 예: 숫자 입력란에 문자 → 재입력 요청/알림/값 초기화.

## 15.3 실무에서 왜 중요한가

* 요구사항을 잘못 이해한 채 구현부터 들어가면 아무리 정교한 코드도 소용없다
* Code Craft가 없으면 **어떤 게 좋은 코드인지, 어떤 게 제품에 좋은 기능인지 스스로 판단할 수 없다**
* 훈련하면 비전공자든 전공자든 Claude Code를 Harness Engineering으로 활용해 빅테크 수준의 기능을 스스로 판단하고 구현할 수 있다

### 15장 정리

1. 알고리즘 정답 속도가 아니라 "요구사항 해석 → 설계 → 트레이드오프 → 확장 가능한 구현" 전략이다.
2. Explore → Brainstorm → Plan → Implement → Verify 5단계로 진행한다.
3. OOD·API·LLD·Product·System Design이 연결돼 있고, Verify의 핵심은 "돌아가는가"가 아니라 **"요구사항을 만족하는가"**다.

# 16장. 기능 요구사항 분석

> **좋은 코드는 문제를 잘 푼 코드가 아니라, 요구사항이 바뀌어도 무너지지 않도록 입력·출력·제약사항·변경 가능성을 먼저 검토한 코드다.**

문제를 받으면 바로 클래스를 만들지 말고 먼저 4가지를 정리한다.

1. 이 기능이 실제로 해야 하는 일은 무엇인가 (기능 요구사항)
2. 입력 데이터는 어떤 형태로 들어오는가
3. 출력은 어떤 형태로 반환되는가
4. 어떤 제약사항과 변경 가능성이 설계를 바꾸는가

## 16.1 왜 바로 코딩하면 안 되는가

문제: **"드라이버의 Payout Calculator를 만들어라."** 이 한 문장만으로 Claude Code는 다음을 알 수 없다.

* Payout 규칙이 무엇인지 · 금액이 라운딩되는지
* 잘못된 배달 기록을 걸러내는 기준 · 보너스·프로모션 처리 방식

그래도 그럴듯한 코드는 나온다. 문제는 **어떤 가정을 했는지, 어떤 제약을 놓쳤는지, 어디가 바뀔 수 있는지를 보장할 수 없다**는 것이다.

> 설계 문제는 문장을 코드로 바꾸는 게 아니라 **모호한 제품 요구사항을 실행 가능한 형태로 바꾸는 작업**이다. 그래서 시키기 전에 **사람이 먼저 Harness Engineering을 해줘야 한다.**

## 16.2 기능 요구사항을 구체적으로 쪼갠다

기능 요구사항 = **시스템이 반드시 해야 하는 행동.** "Payout 계산하기"처럼 추상적이면 부족하다.

Driver Payout Calculator 예:

1. Delivery Record를 입력으로 받는다
2. 각 Record의 Payout을 계산한다
3. 같은 드라이버에 속한 기록인지 구별한다
4. 드라이버별로 Payout을 총 합산한다
5. 잘못된 레코드(다른 드라이버 기록, 잘못된 거리 등)를 처리한다

> 이렇게 나누면 코드 구조가 예상되기 시작한다. 개발자의 프롬프트와 비개발자의 한 문장 프롬프트는 결과가 크게 다른데, **입력·계산·합산·검증의 책임이 분리되어 구현되는지가 갈리기 때문**이다.

**던져야 할 질문**: 사용자는 이 시스템으로 무엇을 하려는가 · 시스템이 해야 하는 액션은 · 반드시 지원해야 하는 흐름은 · 실패·예외 상황은 · 지금 범위와 나중에 확장될 범위는

## 16.3 Input → Logic → Output

모든 시스템은 수많은 입력과 출력이 이어져 만들어진다.

| Input 분석 | Output 분석 |
|---|---|
| 입력 Type | 데이터 타입 |
| 필수 vs 선택 데이터 | 정렬 기준 |
| 데이터 출처 | 금액 단위, 라운딩 규칙 |
| 유효성 조건 | 에러 반환 방식 |
| 중복 가능성 | 빈 입력(Empty Input) 처리 |
| 정렬 여부 | |
| Null/Empty 가능성 | |

> **Input 예**: Delivery Record에는 기본 요금·거리·팁·지역이 있어야 계산된다. 거리가 음수일 수 있는지, 팁이 없을 수 있는지, 이미 정렬돼 들어오는지까지 따진다. **발견하지 못한 가정은 나중에 버그가 된다.**
> **Output 예**: 총 금액 하나만 반환할 수도, 드라이버별 리스트를 반환할 수도 있다. **입출력을 제대로 정의해야 테스트도 제대로 검증할 수 있다.**

## 16.4 제약 분석

제약의 종류: **정확성 · 성능 · 일관성 · 보안/권한 · 확장성 · 테스트 가능성**

| 문제 유형 | 중요한 제약 | 처방 |
|---|---|---|
| 금액 계산 | 정확성 | float 대신 **decimal/정수(cent)**로 소수점 오차 방지 |
| 실시간 랭킹 | 성능·최신성 | 매번 전체 정렬은 느리므로 **캐시·사전계산** |
| 결제 재시도 | 일관성·**Idempotency** | 같은 결제가 두 번 실행되지 않도록 보장 |

## 16.5 변경 가능성 = 분리 후보

* 정책이 자주 바뀌는가
* 계산 공식이 여러 종류인가
* 데이터 출처가 바뀔 수 있는가
* 출력 포맷이 여러 개인가
* 외부 호출이나 DB가 바뀔 수 있는가

> 변경 가능성이 높은 부분은 **"분리 후보"**로 표시한다. Claude Code에게 *"변경 가능성이 높은 부분은 분리 후보로 두고 구현해줘"*라고 하면 프롬프트 자체가 달라진다.

**디자인 패턴은 변경 가능성에서 나온다.** Payout 규칙이 하나면 단순 함수로 충분하다. 하지만 지역별 규칙 + 시간대별 보너스 + 프로모션별 계산이 붙으면 이야기가 다르다. 구현 전에 **"단순하게 갈 것인가, 패턴으로 분리할 것인가"**를 판단한다. 패턴 자체를 몰라도 괜찮다 — Claude Code가 추천·적용해줄 수 있다. (상황별 패턴 매핑 → 20장)

## 16.6 요구사항 분석 템플릿

| 항목 | 내용 |
|---|---|
| 기능 요구사항 | 반드시 해야 하는 일 (Happy Path + 예외) |
| 입력 | 타입, 필수 필드, 선택 필드 |
| 출력 | 타입, 형식, 라운딩·에러 처리 |
| 제약사항 | 정확성·성능·일관성·보안·확장성 |
| 변경 가능성 | 분리 후보로 표시할 부분 |
| (선택) 디자인 패턴 | 필요하면 Claude Code에게 추천받기 |

### 16장 정리

1. 코딩 전에 기능 요구사항·입력·출력·제약사항·변경 가능성을 먼저 분석한다.
2. 모든 시스템은 Input → Logic → Output. 입력은 타입·필수·출처·유효성·중복·정렬·Null을, 출력은 타입·정렬·단위·라운딩·에러를 구체적으로 정의해야 테스트도 검증된다.
3. 제약사항과 분리 후보를 미리 찾아두면 패턴이 필요한 지점과 프롬프트가 훨씬 구체적이고 정확해진다.

# 17장. 좋은 설계란 무엇인가

> **좋은 설계는 완벽한 구조가 아니라, 사람에게 친절한 구조다.**

코드는 컴퓨터가 실행하지만 읽고 고치고 확장하는 건 사람이다. 좋은 설계 = 시스템을 더 쉽게 이해하고 발전시키고 사용할 수 있도록 조직화하는 것. **완벽한 구조가 아니라 현재 요구사항에 맞는 합리적 선택.**

> **잘 정리된 집**: 부엌엔 요리 도구, 욕실엔 세면도구, 옷장엔 옷. 숟가락이 욕실에 있으면 집은 존재해도 살기 어렵다. 로그인 코드는 로그인 쪽에, 결제는 결제 쪽에 있어야 문제가 생겼을 때 어디를 볼지 바로 안다.

## 17.1 다섯 원칙

| 원칙 | 한 줄 정의 |
|---|---|
| **모듈화** | 레고처럼 부품을 바꿀 수 있게 |
| **관심사의 분리** | 각자 자기 일만 하게 |
| **적응 가능성** | 나중에 바뀔 것을 미리 예상 |
| **직관성** | 처음 보는 사람도 덜 헷갈리게 |
| **캡슐화** | 내부의 복잡함을 숨기고 버튼만 제공 |

다섯 원칙을 요구사항과 트레이드오프에 가중치를 두고 **의도적으로 조합**한 결과가 좋은 설계다. 정답보다 중요한 건 **트레이드오프를 설명하고 왜 이 구조를 선택했는지 판단하는 능력.** 판단 기준은 **단순함 · 변경 가능성 · 테스트 가능성 · 유지보수성.**

**모듈화** — 레고 자동차의 바퀴가 마음에 안 들면 바퀴만 바꾼다. 컴퓨터도 램이 부족하면 램만, 저장공간이 부족하면 SSD만.
> 결제에 Stripe를 쓰다 PayPal로 바꿀 때 **결제 부분만** 바꾸면 된다. 앱 전체를 고쳐야 한다면 모듈화가 안 된 것이다.
> 필요 조건: **교체 가능성 · 높은 호환성 · 독립성 · 느슨한 결합**

**관심사의 분리** — HR은 채용, 마케팅은 홍보, 회계팀은 재무. 한 사람이 채용도 회계도 광고도 서버 관리도 하면 처음엔 빨라도 **나중엔 누가 무엇을 책임지는지 알 수 없다.** 소프트웨어도 로그인은 로그인만, 결제는 결제만, 저장은 저장만. 나쁜 설계는 만능 직원 한 명에게 다 시키는 것 — 처음엔 편해도 **아무도 손대기 어려운 파트**가 된다.

**적응 가능성** — 작은 카페에 손님이 늘면 주문 시스템·동선·재고 관리가 달라져야 한다. 처음부터 대기업처럼 만들 필요는 없지만 **확장할 수 있는 구조는 있어야** 한다. 100명 예상하고 만든 걸 10만 명 때 전부 다시 만들어야 하면 설계가 약한 것.
⚠️ 단, **모든 것을 유연하게 만들면 오히려 복잡해진다.** 좋은 설계는 **바뀔 가능성이 높은 부분만 유연하게, 안정적인 부분은 단순하게** 둔다.
> 예: DoorDash 기본 요금 **"정책"**은 회사가 성장하며 바뀌니 유연하게. 하지만 기본 요금을 계산하는 **"로직"** 자체는 안정적이다.

**직관성** — 엘리베이터 위/아래 화살표가 이상하게 배치되면 어느 버튼을 누를지 헷갈린다. 기능은 있는데 쓰기 어려우면 좋은 설계가 아니다. 코드도 처음 보는 사람이 "로그인 문제는 여기", "결제 계산은 여기"라고 예상할 수 있어야 한다.
⚠️ 직관적 ≠ 단순함. 복잡한 문제는 복잡할 수밖에 없다. 좋은 설계는 그 복잡함을 한 곳에 뭉치지 않고 **이해 가능한 단위로 분리**한다.

**캡슐화** — 전자레인지 내부 회로를 몰라도 버튼만 누르면 되고, 엔진 구조를 몰라도 핸들·브레이크·액셀로 운전한다. 결제 API도 내부적으론 카드 검증·재시도·토큰화를 하지만 쓰는 쪽은 `결제하기()` 하나만 호출하면 되게 감춘다.

## 17.2 골디락스 범위

설계 품질은 **절대적이지 않다.** 어떤 요구사항에서 훌륭한 설계가 다른 요구사항에선 부적절할 수 있고, 한 규모에서 잘 되는 설계가 다른 규모에선 실패한다.

* **Over Engineering** — 요구사항에 비해 과하게 설계
* **Under Engineering** — 요구사항에 비해 부족하게 설계

단순한 설계가 자동으로 좋은 것도, 복잡한 설계가 자동으로 나쁜 것도 아니다.

X축 복잡도, Y축 이상성(설계 품질)으로 보면 다섯 구간이 나온다.

| 구간 | 특징 |
|---|---|
| 모호한 모놀리스 | 복잡도는 낮아 보이지만 구조가 너무 모호함 |
| 단순 설계 | 어떤 문제엔 적절하나 요구사항이 커지면 부족 |
| **골디락스 범위** | 적절한 복잡도에서 이상성이 가장 높음 |
| 복잡한 설계 | 필요한 복잡도일 수 있지만 과하면 이상성 하락 |
| 비현실 | 너무 복잡해 실제로 쓰거나 유지하기 어려움 |

> **목표는 문제에 적절한 골디락스 범위를 찾는 것.**

## 17.3 결합도와 응집도

| 개념 | 의미 | 목표 |
|---|---|---|
| **응집도 (Cohesion)** | 관련 데이터·동작이 한 모듈 안에 얼마나 촘촘히 뭉쳐 있는가 | **높을수록** 좋음 |
| **결합도 (Coupling)** | 한 모듈이 다른 모듈과 얼마나 많이 연결·의존하는가 | **낮을수록** 좋음 |

모듈을 박스로 그렸을 때 안의 요소가 흩어져 있으면 응집도가 낮고, 촘촘하면 높다. 다른 모듈을 이것저것 갖다 쓰는 연결이 많을수록 결합도가 높다.

느슨한 결합이면 복잡도가 줄고, 의도치 않은 수정·오용을 방지하며, 유지보수성이 개선된다. **한 모듈 내부 변경이 바깥에 영향을 주지 않아 의존하는 쪽을 깨뜨리지 않고 배포할 수 있다.**

| | 응집도 낮음 | 응집도 높음 |
|---|---|---|
| **결합도 높음** | 잘못 선택된 경계 — 작은 그룹이 어설프게 나뉘어 복잡하게 얽힘 | 하나의 큰 덩어리 — 관련은 있지만 너무 많은 요소·책임이 몰림 |
| **결합도 낮음** | 파괴적 탈결합(Destructive Decoupling) — 연결은 적지만 의미 있는 경계·응집이 부족해 조각만 흩어짐 | **이상적인 모듈 구조** |

> **응집도는 높이고 결합도는 낮추되, 완전히 단절시키는 게 아니라 꼭 필요한 연결만 남긴다.** 무조건 잘게 쪼개 연결을 끊으면(파괴적 탈결합) 응집도까지 낮아지고, 관련 없는 책임까지 몰아넣으면 하나의 큰 덩어리가 된다.

### 17장 정리

1. 좋은 설계 = 사람이 이해·수정·확장하기 쉬운, 현재 요구사항에 맞는 합리적 선택. 모듈화·관심사 분리·적응 가능성·직관성·캡슐화로 만들어진다.
2. 설계 품질은 절대적이지 않으므로 Over/Under Engineering 사이의 **골디락스 범위**를 찾는다.
3. 모듈 구조는 결합도(낮게)와 응집도(높게)로 판단하되, **꼭 필요한 연결은 남긴다.**

# 18장. OOD — 요구사항을 클래스와 책임으로

> **OOD는 큰 문제를 작은 책임으로 분할하고, Claude Code가 안전하게 구현할 수 있는 구조를 만드는 방법이다.**

쉽게 말하면 **큰 문제를 작은 역할로 나누고, 각 역할이 자기 일만 하게 만드는 설계 방법.**

## 18.1 왜 함수 하나로 끝내면 안 되는가

```python
def calculate_delivery_fee(order):
    return 5000
```

실제 서비스는 이렇게 단순하지 않다. 비 오는 날엔 추가 요금, 프리미엄 고객은 할인, 주문 금액이 높으면 무료 배송.

요구사항이 늘수록 함수 하나가 너무 많은 일을 한다 — 거리 계산·날씨 계산·할인·취소 주문 검증이 전부 한 곳에 섞인다. "눈 오는 날 추가 요금도", "신규 고객 첫 주문 무료 배송도" 같은 요구가 붙을 때마다 **같은 함수를 계속 고쳐야 하고, 함수가 끝없이 커진다.**

> **비유**: 학교 단체 프로젝트에서 한 사람이 자료 조사·발표 자료·발표·디자인·질문 답변을 전부 하면 힘들다. 그래서 역할을 나눈다. 코드도 **주문 데이터 담당 / 입력 검증 / 기본 배송비 계산 / 추가 요금 계산**처럼 나눈다.

## 18.2 책임에서 클래스로

**책임은 요구사항에서 나오고, 그 책임이 클래스가 된다.**

| 요구사항(책임) | 클래스 |
|---|---|
| 주문 정보를 받는다 | `Order` |
| 잘못된 주문인지 확인한다 | `OrderValidator` |
| 기본 배송비를 계산한다 | `BaseFeePolicy` |
| 추가 요금(날씨·거리)을 계산한다 | `SurchargePolicy` |
| 할인을 계산한다 | `DiscountPolicy` |
| 최종 배송비 결과를 반환한다 | `DeliveryFeeResult` |

⚠️ **클래스 이름을 먼저 외우면 안 된다.** 그전에 물어야 할 것:
**"이 기능이 해야 되는 일은 무엇인가?" → "그 일들 중 서로 다른 책임은 무엇인가?" → "각 책임을 누가 맡으면 좋을까?"** — 그 답이 곧 클래스다.

## 18.3 클래스 vs 오브젝트

```python
class Order:
    pass

order_1 = Order()
order_2 = Order()
```

* **클래스** = 설계도 — "주문은 이런 정보를 가져야 해"를 알려주고 **하나의 책임을 고정**한다
* **오브젝트** = 그 설계도로 만들어진 실제 (예: 실제로 들어온 123번 주문)

`order_1`과 `order_2`는 같은 설계도에서 나왔지만 서로 다른 실제 주문이다.

## 18.4 객체 3종 — Entity / Value Object / DTO

| 종류 | 기준 | 예시 |
|---|---|---|
| **Entity** | **ID**가 중요 | `Order`, `Customer`, `Driver` — 금액 등 다른 값이 바뀌어도 ID가 같으면 같은 대상 |
| **Value Object** | **값의 묶음**이 중요 | `DeliveryFeeResult`(기본+추가+할인+최종), `Money`, `Distance` |
| **DTO** | **전달 모양**이 중요 | `DeliveryFeeResponseDTO` — API 응답으로 화면·다른 서버에 값을 전달 |

## 18.5 정리

* 큰 기능을 작은 책임으로 나눈다
* 각 책임에 이름을 붙인다 → **클래스**
* 실제 데이터 하나하나 → **오브젝트**
* 바뀔 수 있는 부분은 **Policy / Interface**로 분리
* 전체 흐름은 **Service**로 조합
* 마지막으로 **테스트**로 검증

> OOD는 요구사항에서 책임을 찾아 코드 안에서 안전하게 나누는 기술이다. **Claude Code에게 좋은 코드를 만들게 하려면 사람이 먼저 이 책임 구조를 잡아줘야 한다.**

### 18장 정리

1. 한 함수에 다 몰아넣는 대신 큰 문제를 작은 책임으로 나누고 각 역할이 자기 일만 하게 한다.
2. 요구사항에서 책임을 찾아 클래스로 바꾼다. 클래스는 설계도, 오브젝트는 그것으로 만들어진 실제.
3. ID가 중요하면 Entity, 값의 묶음이면 Value Object, 전달 모양이면 DTO.

# 19장. Harness Engineering을 위한 SOLID

> **좋은 코드는 똑똑한 함수 하나로 만들어지지 않는다. 책임·제약·검증이 나뉜 구조에서 나온다.**

문제를 받으면 판단할 수 있어야 하는 것:

* 이 기능에서 자주 바뀔 수 있는 부분은 어딘가
* 한 클래스가 너무 많은 일을 하고 있지는 않나
* **Claude Code가 이 코드를 수정할 때 어디까지 건드리게 될까**

Claude Code에서 모델은 판단만 하고 실행은 Harness가 통제한다(2장). CodeCraft도 똑같이 **책임·제약·검증이 나뉜 구조**가 필요하다. 그 기준이 SOLID다.

## 19.1 미니 케이스 — 넷플릭스 시청 기록 요약 API

문제: **사용자의 시청 기록 요약을 반환하는 API를 만들어라.**

월요일에 드라마 20분, 화요일에 같은 에피소드 15분, 수요일에 다른 영화 40분. 이런 이벤트가 쌓이면 앱은 최근 본 콘텐츠·이어보기·진행률·마지막 시청 시간을 보여준다.

즉 **여러 시청 이벤트를 모아 사용자가 보기 좋은 형태로 정리해주는 API**다. 같은 영상을 여러 번 봤으면 합치고, 마지막 시청 시간이 필요하고, 진행률도 계산해야 한다.

**한 함수로 시작하면**

```python
def get_watch_history(user_id):
    events = ...      # 이벤트를 받아온다
    result = ...       # 이벤트들을 처리한다
    return result
```

요구사항이 "최근 본 콘텐츠", "콘텐츠별 진행률" 둘뿐일 땐 문제없다. 하지만 완료 상태를 다르게 집계하거나, 국가별로 다르게 표시하거나, 오늘은 최근 순 내일은 추천 점수 순으로 바뀌면 **`if`가 끝없이 쌓인다** — 데이터 가져오기 · 권한 필터링 · 시청 시간 합치기 · 진행률 계산 · 완료 여부 판단 · 정렬이 전부 한 함수에.

**목표 구조 — 책임별로 나누기**

| 클래스 | 책임 |
|---|---|
| **WatchHistoryService** | 전체 흐름을 **조합만** 한다 (직접 수행하지 않음) |
| **WatchEventRepository** | 시청 이벤트를 가져온다 |
| **WatchEventValidator** | 잘못된 이벤트를 걸러내고 볼 수 있는 콘텐츠인지 판단 |
| **ProgressCalculator** | 진행률 계산 |
| **WatchStatusPolicy** | `IN_PROGRESS` / `COMPLETED` 판단 |
| (정렬 기준) | 최근 순, 추천 점수 등 |
| (응답 조합) | API 응답 모양 |

## 19.2 SOLID 5원칙

| | 원칙 | 질문 | Claude Code 관점 |
|---|---|---|---|
| **S** | Single Responsibility | 이 클래스는 **왜** 바뀌는가, 이유가 하나인가 | **수정 범위를 좁힌다** |
| **O** | Open-Closed | 새 정책마다 기존 코드를 고쳐야 하는가 | 고칠 곳/건드리면 안 될 곳이 명확해진다 |
| **L** | Liskov Substitution | 바꿔 끼워도 같게 동작하는가 | 계약을 명시해 새 구현체를 안전하게 추가 |
| **I** | Interface Segregation | 필요 없는 기능까지 강요하는가 | **실수할 공간이 작아진다** |
| **D** | Dependency Inversion | 서비스가 구현을 직접 만드는가, 외부에서 받는가 | 수정 범위·**토큰 사용**을 줄인다 |

**S — 수정 범위를 좁힌다**
`WatchHistoryService`가 DB 조회·이벤트 검증·콘텐츠 숨김·진행률·완료 판단·정렬·응답을 전부 하면, **DB 구조가 바뀌어도 정책이 바뀌어도 정렬이 바뀌어도 전부 이 파일 하나를 고쳐야 한다.**
→ `WatchEventRepository`(로딩) / `WatchEventValidator`(검증) / `VisibilityPolicy`(볼 수 있는 콘텐츠인지) / `ProgressCalculator`(진행률)로 분리.
> "필터링 정책만 바꿔줘" → `VisibilityPolicy`만 보면 된다. 다 섞여 있으면 정렬·진행률·응답 생성 코드까지 건드릴 위험이 있다.

**O — 확장에 열려 있고 수정에 닫혀 있게**
정렬 기준이 "최근 순 → 많이 본 순 → 추천 점수 순"으로 늘어날 때 `if`를 추가하는 대신 `RecentWatchSortPolicy`, `MostWatchSortPolicy`처럼 `SortPolicy`를 나눈다.
> 그러면 새 정책(`RecommendationSortPolicy`)이 필요할 때 **"새 정책을 추가해줘, 기존 정책은 건드리지 마"**라고 Harness Engineering을 적용할 수 있다.

**L — 같은 역할이면 바꿔 끼워도 똑같이**
`SortPolicy`의 약속은 "아이템들을 받아 정렬된 아이템들을 반환한다". 어떤 구현체든 이 약속을 지켜야 `WatchHistoryService`가 동일하게 쓸 수 있다. 아무것도 반환하지 않거나 가끔 다르게 동작하면 위반이다.
> 새 정책을 만들게 할 땐 계약을 명시한다: *"아이템들을 입력받고 정렬된 새 목록을 반환할 것, 원본을 직접 수정하지 말 것, `VisibilityPolicy`의 책임을 침범하지 말 것."*

**I — 큰 계약 하나보다 작은 계약 여러 개**
인터페이스는 "이 역할을 맡으려면 이런 기능을 제공해야 한다"는 **약속(명세)**이다. 로직을 갖지 않는다.
`WatchHistoryPolicy` 하나에 `ValidateEvent`·`CheckVisibility`·`CalculateProgress`·`Sort`·`BuildResponse`를 다 넣으면 **필요 없는 메서드까지 구현하려다 빈 메서드·잘못된 기본값·책임이 섞인 코드**가 나온다.
→ 작게 나누면 "너는 visibility만", "너는 progress만"처럼 경계를 작게 줄 수 있다.

**D — 특정 구현에 묶이지 않게**
> 나쁨: `WatchHistoryService`가 내부에서 `RecentWatchSortPolicy`, `AdultProfileVisibilityPolicy`를 직접 생성
> 좋음: `SortPolicy`, `VisibilityPolicy`를 **외부에서 전달받아** 사용

직접 만들면 새 정책마다 서비스 코드를 고쳐야 하고, 외부에서 받으면 **새 클래스를 추가하고 설정만 바꾸면 된다.**

### 19장 정리

1. 한 클래스에 조회·검증·계산·정렬·응답을 몰아넣으면 요구사항이 늘수록 수정 범위가 커지고 Claude가 건드릴 위험도 커진다.
2. SOLID = 책임을 나누는 기준 — 책임 분리(S), 추가로 확장(O), 교체 가능(L), 작은 인터페이스(I), 외부 주입(D).
3. 적용하면 **"이 정책만 바꿔줘", "새 정책만 추가하고 기존 건 건드리지 마"**처럼 지시할 수 있어 수정 범위와 토큰을 줄인다.

# 20장. 미니 케이스 — Delivery Fee Calculator

> **Claude Code의 코어 루프와 Harness 구조를 그대로 CodeCraft에 적용한다.**
> 코어 루프·Harness 정의는 1~2장, Deny First·Layered Control은 6장, Generation/Evaluation은 7장, Context Reduction Pipeline은 3장 참고. 이 장은 그것을 **실제 문제에 적용**한다.

## 20.1 하네스 대응시키기

| Claude에게 시킬 일 | 요구사항 Harness가 할 일 |
|---|---|
| 설계 후보(옵션) 생각하기 | Input/Output 정의 |
| 패턴 후보 제안하기 | 제약 조건 통과시키기 |
| 구현 방향 만들기 | 엣지 케이스를 테스트로 바꾸기 |
| | 구현이 요구사항을 벗어나지 않게 하기 |

> 모델은 판단만 하고 바로 실행되지 않는다. 실행 전 Harness가 권한을 확인하고 위험을 막고 결과를 되돌린다. **CodeCraft도 똑같다** — "이렇게 구현하면 되겠다"로 바로 가지 말고, 그 설계가 **입력 조건을 만족하는지 · 출력을 지키는지 · 제약을 위반하지 않는지 · 엣지 케이스를 통과하는지** 먼저 확인한다.

## 20.2 Deny First를 코드 설계에

* 모르는 요구사항은 그냥 가정하지 않는다
* 위험한 입력은 허용하지 않는다
* 애매한 정책은 코드 안에 숨기지 않는다

## 20.3 문제 — Delivery Fee Calculator

> **"Build a service that calculates delivery fees for customer orders."**

단순해 보이지만 이 문장만 보고 코드를 짜면 중요한 맥락을 놓친다.

**Deny First 질문**

* 거리가 음수면 계산하지 않는가, 아니면 클램프(clamp)로 정책을 명확히 하는가
* 도시(city)가 비었을 때 "서울"로 가정해도 되는가 → **안 된다**
* 거리가 음수인데 그냥 계산해도 되는가 → **안 된다**
* 고객 타입이 이상한 값일 때 "Regular"로 처리해도 되는가 → **명확히 정해야 한다**

**Context Harness**

| 항목 | 내용 |
|---|---|
| 모호한 문제 | "배달 수수료 계산기를 만들어라" |
| 입력 | 주문 금액, 배달 거리, 도시, 고객 타입, 날씨, 주문 상태 |
| 출력 | 기본 배송비, 추가 요금, 할인 금액, 최종 배송비(**음수 불가**) |
| 제약 | 음수 거리 금지, 취소 주문 제외, 최종 배송비 음수 금지 |
| 변경 가능성 | 도시별 요금, 날씨별 추가 요금, 멤버십 할인, 프로모션 정책 |

> 거리·금액이 높으면 무료 배송인지, 비·눈이면 추가 요금인지, 도시마다 기본 요금이 다른지, 프리미엄은 할인인지 — **정리되지 않으면 Claude도 사람도 코드도 전부 추측으로 움직인다.**

**진짜 병목은 Context Window가 아니다.** CodeCraft에서는 **문제 맥락을 얼마나 정확히 잡았는가**가 병목이다. 문제 프롬프트는 보통 짧고, 그것만 보고 만들면 추측이 섞인다. 그래서 **요구사항 분석 과정이 곧 CodeCraft의 Context Harness**이며, 비개발자와 전문 개발자의 결과물 갭도 여기서 갈린다.

## 20.4 확장 메커니즘 → 디자인 패턴

| Claude Code 확장 | 역할 | | CodeCraft 상황 | 패턴 |
|---|---|---|---|---|
| MCP | 외부 시스템 연결 | | 계산 정책이 교체될 때 | **Strategy** |
| Skills | 반복 작업을 능력화 | | 상황별 객체 생성 | **Factory** |
| Hooks | 라이프사이클 중간 개입 | | 데이터 출처 분리 | **Repository** |
| Plugin | 기능 확장 | | 외부 API 연결 | **Adapter** |

> 모든 문제를 하나의 패턴으로 풀 수는 없다. **상황별로 쓸 수 있는 패턴이 다르다.**

## 20.5 책임 분리

Subagent가 Parent Context와 분리돼 작은 작업을 수행하듯(11장), 좋은 설계도 큰 책임을 작은 단위로 분리한다.

입력값 검증 · 기본 배송비 계산 · 날씨/거리/시간대 추가 요금 · 멤버십/쿠폰/무료배송 할인 · 최종 결과 반환(Result)

⚠️ **나쁜 설계**: 하나의 함수(Calculator) 안에 이 모든 책임을 넣는 것. 함수는 입력→출력 구조인데 그 안에서 여러 작업을 한꺼번에 하면 좋은 설계가 아니다. 독립된 작업을 각각 분리해야 **유지보수 비용·확장성·패턴 적용** 면에서 좋다.

## 20.6 5단계 검증 레이어 — Safety Harness

> **안전장치는 하나에만 의존하면 안 된다** — Layered Control(6장)을 코드에도 쌓는다.

| 레이어 | 검증 내용 |
|---|---|
| **1. Type** | 타입을 제한 |
| **2. Input 검증** | 음수 금액 금지, 음수 거리 금지, city 필수 |
| **3. 정책 검증** | 무료 배송 기준, 할인 적용 순서, 요금 적용 조건 |
| **4. 결과 검증** | 최종 요금이 음수가 될 수 없다 |
| **5. 테스트** | Happy Path + 예외 케이스 |

**Generation / Evaluation 분리**(7장)를 이 문제에 적용하면:

| 단계 | 내용 |
|---|---|
| **Generation** | Policy 구현, Validator 구현, Service 구현 |
| **Evaluation** | 정상 주문 / 비 오는 날 요금 / 무료 배송 기준 테스트 |

## 20.7 관통하는 원칙 10

* **모델보다 Harness, 코드보다 요구사항 Harness가 먼저다** — 그 위에 여러 Harness를 겹겹이
* **Reasoning(판단)과 Execution(실행)은 분리**
* **모호한 요구사항과 위험한 능력을 그대로 허용하지 않는다** — Deny First
* **텍스트(컨텍스트)는 희소 자원** — 문제 맥락을 선별하고 명시
* **디자인 패턴은 상황별로** — 하나를 억지로 끼워 맞추지 않는다
* **책임을 분리** — 한 함수·모듈에 여러 역할을 몰아넣지 않는다
* **정책도 격리** — 바뀔 수 있는 정책은 로직과 분리
* **왜 이 설계를 선택했는지 설명 가능해야** — 트레이드오프를 근거로
* **구현과 테스트를 분리** — Generation/Evaluation
* **최종 판단은 사람이** — Human Decision Authority(2장)

## 20.8 실제 적용

에이전트 루프로 **요구사항 분석 → 설계 → 구현 → 테스트**를 반복하게 만들고, 그 위에 Harness를 얹는다.

| Harness | Delivery Fee Calculator에서 |
|---|---|
| **Context** | 주문 금액·거리·도시·날씨·고객 타입 등 맥락 수집·검증 |
| **Permission(제약조건)** | 음수 거리 금지, 취소 주문 제외 같은 제약을 검증하는 게이트 |
| **설계 방안** | 상황에 맞는 디자인 패턴 선택 |
| **Verification** | Compaction, Subagent, Test로 결과 검증 |

이 외에 Tool·Persistence·Subagent Harness와 최소 구현·테스트까지 함께 적용된다.

### 20장 정리

1. 코어 루프와 Harness는 CodeCraft에도 그대로 적용된다 — 설계도 바로 실행하지 않고 입력·출력·제약·엣지 케이스를 먼저 확인하고, Deny First로 모르는 요구사항을 가정하지 않는다.
2. 진짜 병목은 Context Window가 아니라 **문제 맥락의 정확성**이며, 확장 메커니즘은 Strategy·Factory·Repository·Adapter로 대응된다.
3. 검증은 Type → 입력 → 정책 → 결과 → 테스트 5단계로 쌓고, 책임·정책을 분리하고 구현과 테스트를 분리하며, 최종 판단은 사람이 한다.
